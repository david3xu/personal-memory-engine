# Engine and adapter boundaries

The Rust engine owns the recording contract and validated operations. It has no database, MCP, desktop, network, or hosting dependency. `DecisionRepository` is its persistence port; callers cannot construct `ValidatedCapture` without validation. Rust declarations generate the portable JSON schemas and TypeScript types. CI rejects stale generated contracts and concrete host dependencies in the engine.

`crates/local-runtime` composes adapters. SQLite atomically appends versions and serializes competing writers with immediate transactions. Exact retries return the same version; reusing a request ID with different content fails. Revisions must refer to the current version of the same decision. Database triggers reject update/delete of individual versions, and a newer database version is rejected without migration. This is application integrity, not protection against a local owner editing the file directly.

The stdio MCP helper exposes `record_decision`, `list_decisions`, and `decision_history`. The worker starts a helper process pointing at the same local database as the owner app. No chat monitoring, inference model, or network listener is introduced. The process writes only MCP protocol messages to stdout. Tool errors do not claim persistence. Last tool-use time remains activity metadata, not proof of a live or authenticated worker connection. The separate connection adapter coordinates worker access using a cross-process lock and durable private setup metadata. The owner can pause worker reads/writes without mutating card history. A fresh synthetic request ID receives a verification receipt only after a successful record; metadata write failure never reports a committed save as failed.

The Tauri host and TypeScript view are separate delivery components. Their job is to display validated records and user-facing connection/setup states. They must not duplicate engine rules or silently edit earlier versions. New integrations enter through adapters; core changes require semantic and compatibility review under the contribution guide. These modules are contribution boundaries, not executable third-party plugin loading.

`crates/public-snapshot` positively projects only selected presentation fields and renders escaped, self-contained HTML. CI keeps this crate independent of transport, filesystem, storage and provider dependencies. `crates/github-publication` publishes that HTML through the bundled official GitHub CLI; it does not access SQLite. `crates/local-runtime/src/sharing.rs` freezes previews and persists a private publication ledger with atomic writes and cross-process locking. Owner commands compose those pieces; MCP exposes no publication operation.

Each publication has its own URL. Private revisions do not alter it. The adapter uses an isolated orphan Pages branch, refuses unrelated sites/branches and never forces updates. Pending attempts survive interruptions. Only an anonymous exact-byte read advances publication to live or withdrawal to withdrawn. Withdrawal replaces the live content, retaining local decisions and potentially public Git history. Neither MCP recording nor reading a card grants permission to publish. See the [sharing guide](../user-guides/share-decisions.md) for disclosure and credential boundaries.

The desktop prepares an app-owned catalog from bundled plugin resources. Installed manifests refer to a stable launcher in the local data directory; reconnect updates the helper path after app relocation. Neither source checkout paths nor private records are distributed. Constructed plugin/new-chat links carry local setup context only; the test chat is prefilled for the human to send. The TypeScript onboarding module is separate from card/history presentation.
